# Dataset Service 设计文档

> 定位：**把 ClickHouse 里的表，包装成一个个「数据集」给业务方自助查数。**
> 使用方全程看不到 SQL——只勾选维度、指标、加过滤条件，后端负责把「查询意图」编译成 SQL 并执行。
>
> 本文只讲功能要点与设计取舍，不涉及具体代码实现。

---

## 1. 要解决的问题

业务同学想查数，但直接给 ClickHouse 权限成本太高：写不对 SQL、口径各写各的、一个 `SELECT *` 把集群拖垮、还能看到不该看的租户数据。

所以引入一层「数据集（dataset）」抽象：

- 由数据/研发同学在配置页把一个数据集定义好（底层是一段 `mid_sql`）；
- 业务同学在查询页只能在这个数据集划定的范围内勾选和过滤；
- 权限在服务端强制注入，客户端绕不过去。

---

## 2. 整体架构

```
浏览器 (React + antd)
   │  REST /api/v1
   ▼
Go 服务 (gin，单进程单二进制，前端 dist 用 go:embed 打进去)
   ├── MySQL       存数据集配置（唯一有状态的地方）
   └── ClickHouse  跑查询（native 协议，只读账号）
```

- **后端**：Go + gin + GORM；查询引擎抽象成 `Engine` 接口，目前只有 ClickHouse 实现。
- **前端**：React 18 + TypeScript + Vite + Ant Design 5，SQL/JSON 编辑用 Monaco。
- **交付**：`docker build` 出一个镜像，前端产物编译进二进制，**部署时不需要 nginx、不需要挂静态目录**。开发态可用 `STATIC_DIR` 指向磁盘目录，改前端不用重编译 Go。
- **查询是同步的**，没有异步任务、没有结果落库、没有导出中心。查完就完，只留日志。

## 3. 数据模型

单表 `tb_dataset_config`，一个数据集一行。

| 字段 | 类型 | 说明 |
|---|---|---|
| `dataset_key` | varchar(64) | 数据集唯一标识，**全局唯一** |
| `dataset_name` | varchar(128) | 展示名 |
| `mid_sql` | mediumtext | 数据集的 SQL 主体，见第 6 节 |
| `dim_map` | json | 维度：`{"city_name": "city", ...}`，key 是给业务看的名字，value 是真实列/表达式 |
| `mtx_map` | json | 指标：`{"cost": "sum(cost)", ...}` |
| `label_map` | json | 维度/指标的中文含义，纯展示用，不参与 SQL |
| `acl` | json | 权限配置，见第 7 节 |
| `status` | tinyint | 1 启用 / 0 停用 |
| `version` | int | 乐观锁版本号 |
| `created_by` / `updated_by` | varchar | 操作人（来自 `X-User`，只做审计，不做鉴权） |
| `deleted_at` | bigint | 软删除时间戳，0 表示未删除 |

几个刻意的设计：

- **软删除用 `bigint` 而不是 GORM 的 `gorm.DeletedAt`**。MySQL 唯一索引里 NULL 之间互不冲突，用 `DATETIME NULL` 会导致「删了再建同名」时唯一约束失效；改成「0 未删除 / 非 0 为删除时刻」，配合 `uk_dataset_key(dataset_key, deleted_at)` 才真正约束得住。
- **`dim_map` / `mtx_map` 的值是「列表达式」而不只是列名**，所以 `toDate(ts)`、`sum(if(x>0, cost, 0))` 这类都能配置，口径由配置方锁定。
- **`acl` 是 JSON 对象而不是若干独立列**。后续加 `users`、`roles`、读写分离等维度时往对象里塞字段即可，不改表结构、不迁存量数据。
- **改配置带 `version` 乐观锁**，版本冲突返回 409，避免两人同时编辑互相覆盖。

## 4. 配置管理页

功能要点：

- 列表：关键字搜索（key / name）、按状态筛选、分页；列里直接展示维度数、指标数、权限管控情况（租户白名单 + 行级标签）。
- 新增 / 编辑抽屉：
  - `mid_sql` 用 Monaco（SQL 高亮）；
  - `dim_map` / `mtx_map` / `label_map` 用键值对编辑器；
  - `acl` 直接用 JSON 文本编辑（对象结构，方便扩展）；
  - **改动实时校验**：`POST /datasets/validate` 只校验不落库，key 冲突、map 为空、行级规则配错等在保存前就报出来。
- `mid_sql` 的长度上限 1 MiB（`MAX_SQL_BYTES`），防误操作把存储撑爆。
- 删除是软删除，同名 key 删除后可以重新建。

## 5. 查询页：查询意图模型

**核心约束：查询页只有一个执行接口 `POST /api/v1/query/execute`。**

请求体描述的是「我想看什么」，不是 SQL：

```jsonc
{
  "dataset_key": "ad_cost_daily",
  "dims":    ["stat_date", "city_name"],   // 勾选的维度
  "metrics": ["cost", "clicks"],           // 勾选的指标
  "filter":  { ... },                      // 过滤条件树，见下节
  "order_by":[{"field": "cost", "desc": true}],
  "limit":   1000
}
```

SQL 一律由后端组装：

```
SELECT <dim 表达式> AS `xxx`, <metric 表达式> AS `yyy`
FROM ( <mid_sql> ) AS __mid
WHERE ... GROUP BY ... HAVING ... ORDER BY ... LIMIT n
```

设计约定与安全边界：

- **`mid_sql` 的输出被当成「可再次聚合的中间结果」**，外层按用户选的维度重新聚合。好处是指标口径统一、不会因为用户多勾一个维度就算重；代价是配置方要保证 `mid_sql` 的结果能被再次聚合（不能在里面提前 `GROUP BY` 到不可再聚合的形态）。
- **维度/指标/排序/过滤字段全部走白名单枚举校验**——只能填 `dim_map` / `mtx_map` 里配好的 key。
- **唯一的自由输入是过滤值，一律走 ClickHouse 命名参数绑定**（`{p0:String}`），不做字符串拼接。这是整个查询功能唯一的注入面。
- 返回结果里**不含 SQL**；执行失败时把引擎原始错误透出 + `request_id`，拿 id 去日志里捞完整 SQL。

**分页：服务端一次最多返回 10000 行（超出标记 `truncated` 并提示），前端在这批数据上做分页。** 这不是偷懒，是刻意选择——万行以内的场景，前端分页交互更顺滑，也避免了「每次翻页都重新跑一遍 ClickHouse」。排序则相反，交给 ClickHouse 做（见第 9 节）。

## 6. 过滤条件树 与 WHERE / HAVING

### 6.1 条件树

过滤条件是一棵**可任意嵌套的树**，不再是扁平的 AND 列表：

- 分组节点：`{logic: "and"|"or", children: [...]}`
- 叶子节点：`{field, op, value|values}`

这样才能表达 `A AND (B OR C)` 这类组合。规模上限：嵌套 ≤ 5 层、节点 ≤ 64 个。

操作符白名单：`= != > >= < <= like in not in`。**指标（聚合值）上不支持 `like`** —— 与其让 ClickHouse 抛晦涩的类型错误，不如在组装阶段就拒绝并说明原因。

### 6.2 WHERE 还是 HAVING

这是本模块最关键的一条语义：

- **维度条件是行级的**，聚合前就能筛掉大量数据 → 优先下压到 `WHERE`；
- **指标只有聚合后才有值** → 只能进 `HAVING`。

编译规则：

- **AND 可以拆**：能下压的进 `WHERE`，压不下去的进 `HAVING`，两段用 AND 连接后语义等价。
- **OR 整组必须待在同一段**：一旦一部分进 `WHERE`、另一部分留 `HAVING`，两段之间就变成了 AND，语义完全变了。
- **算不出来就明确报错，绝不生成一条语义不明的 SQL**。典型场景：`渠道 = 抖音 OR 消耗 > 1000`，而渠道没勾选为维度——渠道只能在聚合前筛，消耗只能在聚合后判，二者无法用 OR 连接。这时返回明确的中文错误，而不是悄悄换个口径。

## 7. 权限模型（三层）

登录态通过 HTTP 头传入（页面顶部可手动切换，方便调试与演示）：

| Header | 含义 |
|---|---|
| `X-User` | 操作人，仅审计 |
| `X-Tenants` | 当前登录态的租户列表，逗号分隔 |
| `X-Visible-Users` | 当前登录态可见的用户列表，逗号分隔 |

> ⚠️ **已知边界**：服务本身不校验这些头的真伪，默认由上游网关注入。直接暴露在公网等于权限形同虚设，部署时必须挂在网关后面。

权限只管控**查询页**，配置页不做鉴权。

### 7.1 数据集级：`acl.tenants`

```json
{"tenants": ["t1", "t2"]}
```

- 空 / 不配 = 不限制，所有人可见；
- 非空 = 登录态租户与白名单**有交集**才可见。

查询页的数据集下拉、`query/execute`、`dim-values` 三处都做校验。

### 7.2 列级：`acl.col_tenants`

```json
{"col_tenants": {"stat_date": ["t1"], "cost": ["t1", "t2"]}}
```

- key 是 `dim_map` / `mtx_map` 的键（也就是业务看到的名字）；
- 没配的列默认可见，配了的列要有交集。

后端下发给前端的下拉选项**已经过滤过**；同时服务端会对 `dims` / `metrics` / **条件树里引用到的所有字段**再挡一次（过滤条件最容易漏——它可以引用没被选为维度的列）。

### 7.3 行级：`acl.row_filter`

```json
{
  "row_filter": {
    "tenant": {"enabled": true, "column": "tenant"},
    "user":   {"enabled": true, "column": "uid"}
  }
}
```

把登录态的租户列表 / 可见用户列表，挂到指定的**维度列**上，由服务端合成 `col IN (...)` 追加到 `WHERE`（**聚合前**）。

四条硬性规则：

1. **列表达式只从服务端持有的 `dim_map` 里取**，绝不采信客户端传入的列文本。
2. **行级条件恒定以 AND 追加到 WHERE，不进用户的条件树**。用户树的根可能是 OR，塞进去会让权限条件被 OR 吞掉。
3. **fail-closed（宁可拒，不可放）**：规则开了但登录态对应列表为空 → `IN ()` 不匹配任何行，返回 0 行。**不做「列表为空就当成不限制」的兜底**，也不设超管 bypass。
4. **`dim-values` 也注入同样的行级条件**。否则下拉框会把别的租户下的取值也枚举出来，等于绕过了一半的行级管控。

配置约束：`row_filter` 的 column 必须是 `dim_map` 里的键（行级过滤发生在聚合前，用指标列没有语义），开启但列名为空的配置会被拒绝。

## 8. `mid_sql` 模板：按需裁剪 JOIN

### 8.1 为什么需要

实际的数据集经常要 `LEFT JOIN` 多张维表（城市表、渠道表、客户表……）。但一次查询通常只用到其中一部分维表的字段，**每次都把所有 JOIN 丢给 ClickHouse 是纯浪费**。

所以 `mid_sql` 支持 Go `text/template`：按本次查询实际用到的字段，在模板里决定保留哪些 JOIN。

### 8.2 可用变量与方法

| 变量 | 含义 |
|---|---|
| `.Dims` | 本次勾选的维度（保持选择顺序） |
| `.Metrics` | 本次勾选的指标 |
| `.Fields` | 本次用到的全部字段：维度 + 指标 + 过滤字段 + 行级权限列，去重排序 |
| `.Filters` | 过滤条件里引用到的字段，去重排序 |

| 方法 | 含义 |
|---|---|
| `.Has "x"` | 用到某个字段 |
| `.HasAny "a" "b"` | 用到其中任意一个（不传参 = false，保守不裁剪） |
| `.HasAll "a" "b"` | 全都用到（不传参 = true） |
| `.HasDim` / `.HasMetric` | 只在维度 / 指标范围内判断 |

也提供函数形式 `hasAny .Fields "a"` 供习惯管道写法的人使用。

**注意**：`Fields` 里包含了**行级权限用到的列**，否则模板可能裁掉权限条件依赖的 JOIN —— 结果要么 SQL 报错，要么**权限条件静默失效**，后者更危险。

### 8.3 安全与稳定性边界

- 模板能引用到的只有 `dim_map` / `mtx_map` 的键；过滤值一律走参数绑定，永不进模板文本。**模板只能改变标识符与 SQL 片段，拼不出用户可控的字符串。**
- `missingkey=error`：引用不存在的变量立刻报错，好过静默渲染出 `<no value>` 混进 SQL。
- 渲染结果上限 1 MiB；模板按内容哈希缓存（上限 256 条）。
- 不含 `{{` 的存量 `mid_sql` 原样透传，**老配置零开销、零影响**。
- **渲染失败一律返回 400 并说明原因，绝不回退到「不裁剪」的写法** —— 悄悄换 SQL 会让口径变化，比报错危险得多。

### 8.4 实测结论（ClickHouse 26.9，1000 万行表）

| 场景 | 结果 |
|---|---|
| 谓词下推（把过滤条件写进内层） | 扫描行数 1.00x，**零收益**——CH 自己会做 |
| 分区列被函数包裹 `toYYYYMM(d)=202601` | 3,444,451 行（4.43x），下推也救不了 |
| 维表列过滤（JOIN 场景） | 1.000x 全表扫，**下推完全无效**，只能靠宽表化或预聚合 |
| **JOIN 消除** | 39ms → 25ms；31ms → 11ms（**2.8x**）。扫描行数几乎不变，**收益在 CPU 不在 IO** |
| Projection 命中 | 777,778 → 2,800 行（278x），两种 `mid_sql` 写法都能自动命中 |

**结论**：模板化的价值集中在 **JOIN 消除**（省 CPU），不要把「谓词下推」当成收益点——那是优化器已经做了的事。

### 8.5 使用红线

模板裁剪的是**物理执行计划**，不是语义。写模板时必须保证：**裁剪前后同一组维度/指标的聚合结果一致**。典型踩坑是维表 JOIN 导致行数放大（一对多）后 `sum` 被重复计算——这种 JOIN 不能随便裁，只能宽表化或预聚合。

## 9. 结果展示

- **表格**：列头用 `label_map` 的中文名；前端分页（20/50/100/200）。
- **排序与行数**：在查询构建器里配置（排序字段 + 升降序、返回行数），随查询一起提交给后端由 ClickHouse 排，**不是前端排序**。
- **呈现方式：四个 tab —— 表格（默认）/ 柱状图 / 折线图 / 饼图。**
  - **字段跟着查询走**：结果区不提供二次圈选。第 1 个维度做 X 轴、第 2 个做分组、指标全画成系列；换口径回查询构建器改。
  - **智能推荐**：按「维度数 × 指标数、X 轴是否为时间、类目多少、指标间量级差」在对应 tab 上打「推荐」角标，并在上方写一句理由。**只标记、不自动切换**，用户不会被抢走焦点。纯前端推导，后端接口不变。
  - **不可用即置灰**：饼图要求单指标不分组且类目 3~12 个，折线图至少一个维度；不满足时 tab 置灰 + 悬停说明原因。
  - 刻意只保留三种图：条形/面积只是柱状的排版差异，双轴只服务「量级差极大」这一种特例，后者改为推荐**表格**（看数比看图准）。
  - **饼图悬停显示「数值（占比 x%）」**，占比在前端按总量现算；总量为 0 时退回只显示数值。
  - X 轴标签过多时自动旋转/隐藏，超过 30 个点自动加缩略轴。
  - 空值**不做连接**（`connectNulls: false`）——把缺失点连成线是在编造数据。
  - 系列数上限 12，超了提示收敛维度，避免画出没法看的图。
  - 导出：CSV（带 BOM，Excel 打开不乱码）、PNG。
  - 数值精度：Decimal 在后端就转成字符串返回，不落 float64，避免金额丢精度。

## 10. API 一览

### 配置侧

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/datasets` | 列表（关键字 / 状态 / 分页） |
| POST | `/api/v1/datasets` | 新建 |
| GET | `/api/v1/datasets/:key` | 详情 |
| PUT | `/api/v1/datasets/:key` | 更新（带 `version` 乐观锁） |
| DELETE | `/api/v1/datasets/:key` | 软删除 |
| POST | `/api/v1/datasets/validate` | 只校验不落库 |

### 查询侧

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/query/datasets` | 查询页可选数据集，**已按登录态租户 + 列级白名单过滤**，且不含 `mid_sql` / `acl` |
| POST | `/api/v1/query/execute` | 唯一的执行接口 |
| GET | `/api/v1/datasets/:key/dim-values?field=xxx` | 维度候选值（自动 `DISTINCT`），同样受行级权限约束 |

### 探针

`/healthz`（存活）、`/readyz`（MySQL + ClickHouse 连通性）。

### 错误码语义

`400` 查询意图不合法 · `403` 租户/列级权限不足 · `404` 数据集不存在 · `409` 版本冲突。

## 11. 执行约束（三道防线）

| 项 | 默认值 | 环境变量 |
|---|---|---|
| 单次结果硬顶 | 10000 行（超出截断并标记） | `QUERY_MAX_ROWS` |
| 默认行数 | 1000 | `QUERY_DEFAULT_LIMIT` |
| 并发查询数 | 8（信号量，超了排队） | `QUERY_MAX_CONCURRENCY` |
| 查询超时 | 30s | `QUERY_TIMEOUT_SECONDS` |
| 维度候选值上限 | 1000 | `QUERY_DIM_VALUE_LIMIT` |

超时是**双保险**：context 取消 + ClickHouse 侧 `max_execution_time`。只靠 context，CH 端的查询不一定立刻终止。

**查询日志**：成功和失败都打印 SQL（截断 2000 字节）+ 绑定参数 + 操作人 + 耗时 + 行数。日常排查「这个数是怎么算出来的」、确认行级权限条件是否真的注入，主要靠这条日志。不落库。

## 12. 部署

- `docker compose up -d --build` 起三件套：app + mysql + clickhouse（含 `deploy/mysql/init.sql`、`deploy/clickhouse/init.sql` 初始化脚本）。
- 三个基础镜像（node / golang / alpine）和 `GOPROXY`、`NPM_REGISTRY` 都做成了构建参数。`Dockerfile` 里的默认值全部指向国内加速源（`docker.1ms.run`、`goproxy.cn`、`npmmirror`）。
  **⚠️ 已知的坑：`docker-compose.yml` 的 `build.args` 会静默覆盖 `Dockerfile` 的默认值。** 我们踩过两次：只改 Dockerfile，结果 compose 里的 `${X:-官方名}` 兜底又把官方地址塞回来，`FROM` 直接 Bad Gateway。改源时两处必须同时改。
  （当前 compose 里 `NPM_REGISTRY` 的兜底仍是 `registry.npmjs.org`，与其他项不一致，见第 13 节待对齐问题 6。）
- ClickHouse 必须用**只读账号**（`deploy/clickhouse/init.sql` 里建了 `reader`）。
- 生产环境建议关闭 `AutoMigrate`（`DB_AUTO_MIGRATE=false`），用 `deploy/mysql/init.sql` 建表。
- 本地调试：compose 暴露了 ClickHouse 的 8123，浏览器打开 `http://localhost:8123/play` 就是自带的 Web 控制台，可以直接写 SQL 核对数据。

## 13. 设计取舍与待对齐问题

已经拍板的取舍：

| 决策 | 选择 | 理由 |
|---|---|---|
| 查询接口 | 单接口，用户不感知 SQL | 降低使用门槛，口径可控 |
| 分页 | 一次性取回 ≤1w 行 + 前端分页 | 万行内交互更顺，也少打 CH |
| 权限兜底 | fail-closed，无超管 bypass | 权限配置宁可拒，不可放 |
| 模板渲染失败 | 报错，不回退 | 悄悄换 SQL = 悄悄换口径 |
| 算不出的条件组合 | 明确报错，不猜 | 同上 |
| 结果落库 | 不落，只打日志 | 当前阶段不需要审计与复用 |

**需要和各位对齐的问题：**

1. **登录态的信任边界**：现在 `X-Tenants` / `X-Visible-Users` 由上游网关注入，服务不校验。你们那边的网关能注入吗？还是要在服务内接一套真正的登录态解析？
2. **停用（status=0）的数据集要不要从查询页消失**：目前仍然会出现在下拉里。我倾向于隐藏，但这是个行为变更，想听意见。
3. **`mid_sql` 的口径归口**：模板裁剪能力越强，配置方越容易写出「裁了之后口径就变了」的模板。要不要加一个「同维度组合下裁剪前后结果一致性」的自检？
4. **行级权限目前只支持「IN 白名单」一种形态**。如果有「只看自己部门及下级」这类层级需求，得再扩一种规则类型——现在有吗？
5. **指标口径的二次聚合约定**：外层会对 `mid_sql` 结果再 `GROUP BY`。如果某个数据集的 `mid_sql` 本身已经聚合过（比如带 `GROUP BY`），配置方需要按「可再聚合」的方式写。这条约定要不要落到配置校验里（现在只靠人工保证）？
6. **构建源默认值不一致**：`Dockerfile` 里 `NPM_REGISTRY` 默认是 `npmmirror`，但 `docker-compose.yml` 的 `build.args` 覆盖成了 `registry.npmjs.org`。要不要统一？（不影响功能，只是两套默认值容易让人改错地方。）
