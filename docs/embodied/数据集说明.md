# 具身智能机器人数据平台 · 演示数据集说明

这份数据是为「让看板能真的被分析」而造的：一套完整的
**采集 → 标注 → 质检 → 交付结算** 流水线，四类角色（数采员、标注员、质检员、商务）
各自有一份自己的数据集，外加一份跨环节的全流程视角。

- 时间范围：**2026-10-01 ~ 2026-10-30**（近 30 天）
- 数据量级：**145 万行明细**，ClickHouse 落盘 44.9 MiB（列存压缩后）
- 存放位置：ClickHouse 库 `embodied`（与原有的 `demo` 库并列，互不影响）
- 截图：本目录下 13 张，对应下面「能看出什么」的每一条

---

## 1. 为什么不用 `rand()` 直接撒

均匀随机的数据只能「看」，不能「分析」：每个团队的有效率都是 90.x%，
每条曲线的起伏都是噪声，任何分组都看不出差异。所以这份数据把业务规律写进了生成逻辑：

| 造出来的规律 | 目的 |
|---|---|
| 周末产能降到约 6 成（排班制） | 看板上的周中/周末对比不是噪声 |
| 月初爬产、月末冲当月目标 | 趋势有形状，能讲「为什么月末高」 |
| 10-16 ~ 10-18 三台本体返厂 + 车间检修 | 产能与有效率同步下滑，可以复盘 |
| 晚班有效率比早班低约 5 个百分点 | 班次维度能查出结论，进而排班优化 |
| 采集四组整体偏慢、废片偏多 | 团队排名有真实差距，不是随机波动 |
| 3D 点云 / 动作轨迹的一次通过率更低 | 难度与返修的关系可验证 |
| 新工具 v3.0.0-beta 反而更差 | 「上线新版本 ≠ 效率提升」这类反直觉发现 |
| 月末赶工导致通过率下滑 | 质量与交付节奏的冲突可见 |

所有随机数都来自 `cityHash64(行号, 盐)`，不是 `rand()`：同一份脚本跑两次得到
完全一样的数据，出了问题能复现，也能写进断言。

## 2. 表结构

### 维度表

| 表 | 行数 | 说明 |
|---|---|---|
| `dim_staff` | 438 | 四类角色共用的员工表：数采员 120、标注员 260、质检员 40、商务 18；含团队、职级、城市、入职日期 |
| `dim_robot` | 40 | 机器人本体：5 种机型、4 家厂商、固件版本、所在站点；3 台处于「返厂维修」 |
| `dim_scene` | 16 | 操作场景（叠衣服、倒水入杯、插拔充电枪……），带类别、难度、单价 |
| `dim_customer` | 24 | 客户：行业、区域、分层（战略/重点/一般）、负责商务、账期 |

### 事实表

| 表 | 行数 | 粒度 |
|---|---|---|
| `fact_collection_episode` | 480,000 | 一行 = 一次完整操作片段（episode）：时长、帧数、轨迹点、存储体积、质量分、是否判废与判废原因 |
| `fact_annotation_unit` | 900,000 | 一行 = 一个标注任务单元：标注类型、标注对象数、帧数、工时、返修次数、一次通过、准确率、技能标签（数组） |
| `fact_qc_sample` | 60,000 | 一行 = 一次抽检判定：环节（采集/标注）、缺陷类型、严重等级、判定结果、抽检样本数、返修工时 |
| `fact_delivery_daily` | 10,000 | 一行 = 一个项目在某天的交付批次：交付条数、单价、收入、应收、回款、欠款、毛利率、满意度 |

### 关键汇总量（可直接对数）

| 指标 | 值 |
|---|---|
| 采集有效率 | 90.15%（432,700 / 480,000） |
| 采集总工时 | 28,493 小时（120 人 × 30 天 ≈ 7.9 小时/人/天） |
| 采集存储量 | 110 TB（单集均 0.24 GB） |
| 标注一次通过率 | 89.07% |
| 标注总工时 | 67,081 小时（260 人 × 30 天 ≈ 8.6 小时/人/天，含月末加班） |
| 标注对象总数 | 9,391 万 |
| 抽检样本 | 180,585（约为 采集 + 标注 总条数的 13%） |
| 抽检通过率 | 87.5%（标注 87.1% < 采集 88.1%） |
| 交付条数 | 295,899（有效采集 43.3 万条的 68%，其余为缓冲与积压） |
| 确认收入 | 1,670.2 万元 |
| 回款率 | 39%（30 天窗口内，账期 15/30/45 天，只有账期晚的单子结清了） |

口径之间是互相咬合的，不是各编各的：交付量与有效采集量、抽检量与上游产出、
标注工时与标注员人数、`arrears = receivable - received` 都对得上账。
这样「卖得比采得多」「抽检比例 300%」这类一眼假的数字不会出现。

## 3. 五个数据集

配置由 `deploy/register_embodied_datasets.py` 写入（可重复执行，幂等）：

| dataset_key | 名称 | 主要维度 | 主要指标 |
|---|---|---|---|
| `robot_collection` | 具身—数采明细（近30天） | 日期、数采员、团队、场景、机型、班次、模态、判废原因 | 采集条数、有效条数、工时、帧数、存储量、有效率、人均产出 |
| `robot_annotation` | 具身—标注产出明细（近30天） | 日期、标注员、团队、标注类型、难度、工具版本、涉及技能（多值） | 任务数、标注对象数、工时、返修、一次通过率、平均准确率 |
| `robot_qc` | 具身—质检抽检明细（近30天） | 日期、质检员、环节、缺陷类型、严重等级、判定 | 抽检批次、样本数、缺陷数、合格样本、通过率、返修工时、报废数 |
| `robot_business` | 具身—客户交付与回款（近30天） | 日期、客户、行业、区域、分层、商务、项目、阶段、账期 | 交付条数、收入、合同额、应收、回款、欠款、回款率、毛利率、满意度 |
| `robot_pipeline` | 具身—全流程产能（近30天） | 日期、环节（采集/标注/质检）、员工、团队、场景 | 任务数、产出单元、工时、通过率、人均产出 |

三点设计说明：

1. **中文名放在全局字段名字典里**，key 用的是 `dim_map / mtx_map` 的**键名**
   （`collector`、`customer`），不是 SQL 列名（`collector_name`）。
   用列名注册会导致查询页按键名查不到中文，下拉里直接露出英文键名。
2. **`robot_annotation` 的「涉及技能」是多值维度**：一个标注单元会同时涉及
   「抓取」「力控」「双臂协同」等多个技能。它用 `multi_dim_map` 收拢成一行展示，
   而不是进 `GROUP BY` 拆成多行——后者回答的是「标了几个技能」，不是「这单标了什么」。
3. **`robot_pipeline` 用 `UNION ALL` 把三张事实表对齐到同一口径**
   （任务数 / 产出单元 / 合格单元 / 投入工时），用来回答「今天的产出卡在哪个环节」。

## 4. 能看出什么（截图为证）

### 数采（`01` ~ `03`）
- 每日采集条数呈锯齿：周末掉到 6 成左右；**10-17 当天跌到 7,331 条**（相邻工作日 1.8~1.9 万），
  与 10-16~10-18 的设备返厂窗口对上。
- 团队 × 班次的 18 个组合按有效率排序后是**清晰的三层**：早班 91.99~92.35%、
  中班 90.81~91.34%、晚班 86.87~87.38%。晚班是下一个整改点。
- 判废原因：镜头遮挡 11,743 条、任务未完成 9,942 条居前两位，合计占全部废片的 46%。

### 标注（`04` ~ `06`）
- 6 种标注类型的一次通过率差异明显：2D 框 90.32%、关键点 90.34% 最高，
  3D 点云 85.96%、动作轨迹 87.01% 最低——越难的类型越容易返修。
- 工时结构：2D 框 1.89 万小时、语义分割 1.78 万小时，两类占总量 55%。
- 人员产能榜：Top1 标注对象 1,189 万，腰部在 87 万左右；同时列出通过率，
  产能高的不一定质量好（例：徐明 118 万对象但通过率 86.74%）。

### 质检（`07` ~ `08`）
- 采集与标注两条通过率曲线长期分离（标注更低）；**10-16 ~ 10-18 采集侧跌到 82.5%**，
  与采集产能下滑同期出现，说明是同一个设备问题的两个表现。
- 标注缺陷 TOP：漏标 2,332、错标 1,952、框偏移 1,377——下一轮培训就抓这三项。

### 商务（`09` ~ `10`、`12`）
- 客户收入与欠款并列看：收入接近的客户，欠款可以差 3 倍。
- 分层 × 阶段：战略客户量产交付回款率 90%、一般客户验收阶段只有 10%；
  欠款几乎全部沉淀在一般客户（账期 45 天、无预付款话语权）。
- 收入结构：重点客户 911 万、一般客户 854 万、战略客户 437 万——客户数少但战略客户客单价高。

### 全流程（`11`）
- 三条曲线形状高度一致（同受排班与故障影响），但**量级差一个数量级**：
  标注每天约 3 万单、采集约 1.6 万条、质检约 2 千次。
  月末三条线同时上翘，说明冲量是链路级的，不是某个环节单独加速。

## 5. 怎么重建

```bash
# 1) 建表 + 灌数（约 145 万行）。文件会随容器初始化自动执行，
#    文件名 embodied.sql 排在 init.sql 之前，保证库先存在、授权才授得到。
docker compose up -d clickhouse

# 2) 注册全局字段名 + 5 个数据集，并跑一遍冒烟查询
python3 deploy/register_embodied_datasets.py \
    --base http://localhost:8080

# 只做配置自检（拿真实数仓跑一遍 mid_sql，不写库）
python3 deploy/register_embodied_datasets.py --dry-run
```

已经起过库的环境想单独重灌数据：

```bash
docker exec -i dataset-clickhouse clickhouse-client \
  --user dataset --password ch_pass --multiquery < deploy/clickhouse/embodied.sql
```

脚本可重复执行（每张表先 `TRUNCATE`），且结果确定——因为随机源是哈希不是 `rand()`。

## 6. 已知边界

- **比率指标不参与合计**。合计行对 `通过率 / 有效率 / 回款率 / 平均准确率` 这类
  指标显示「—」，因为它们逐行相加没有含义（有效率相加会得到 1622% 这种一眼错的数）。
  判定规则在 `web/src/utils/format.ts` 的 `isAdditiveMetric`：
  命中 `avg / uniq / quantile…` 或「除以另一个列/聚合」即视为不可加；
  `sum(x) / 3600` 这类除以常数只是换算单位，仍然可加。
- **回款率 39% 不是坏数据**。数据窗口只有 30 天，账期 15/30/45 天，
  账期内的单子只付了预付款与节点款；月初交付的才走到结算。
  看账龄要看「分层 × 阶段」的组合，而不是一个总数。
- **标注工时偏高**（8.6 小时/人/天）。这是把月末赶工算进去的月均值，
  与「月末通过率下滑」是同一件事的两面。
- **客户名与公司名都是虚构的**，只用于演示分组维度，不对应任何真实合同。
- 时间固定为 2026-10，账龄按 `2026-10-30` 计算；如果数据往后延，需要同步改这个基准日。
